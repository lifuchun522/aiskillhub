# Key 问题单

需要外部凭据才能验证的能力，不要在文章里写"这里需要 API Key，请自行配置"就完事。整理成分档问题单，读者（或你的协作方）一眼知道该给什么。

---

## 分档

| 档 | 语义 | 处理方式 |
|---|---|---|
| **T0** | 已经跑通，零 Key | 只做记录，不需要任何东西 |
| **T1** | 最高优先：解锁核心体验 | 一定要拿到，否则文章缺核心证据 |
| **T2** | 次优先：解锁差异化能力 | 尽量拿到，拿不到就写"未验证" |
| **T3** | 可选增强：音色/画质/风格 | 可以跳过 |
| **T4** | 边缘功能：发布、统计、云同步 | 默认跳过 |

T0 存在本身就是结论：**核心链路不需要付费**。

---

## 每条必写四件事

| 项 | 来源要求 |
|---|---|
| 配置字段名 | 从 `config.example.*` 的注释里抄，**不能自己编** |
| 官方获取地址 | 同样是配置文件注释，或项目 README 的链接 |
| 填在哪 | 哪个文件、哪个字段、哪一行 |
| 不填的后果 | 哪个能力不可用，是降级还是直接失败 |

字段名编错等于问题单作废：读者照着填会得到"配置无效"，回头还得问你。

```bash
# 字段名与官方地址都在这里
grep -n -A2 "api_key\|_key\|token" config.example.toml
```

## 模板

```markdown
### T1 解锁文案生成（LLM）

| 项 | 内容 |
|---|---|
| 需要字段 | `llm_provider`、`openai_api_key` |
| 获取地址 | https://platform.openai.com/api-keys |
| 填写位置 | `config.toml` → `[llm]` 段 |
| 不填的后果 | 只能手填脚本，无法自动生成文案与关键词 |

### T2 解锁商业音色（Azure TTS）

| 项 | 内容 |
|---|---|
| 需要字段 | `azure_speech_key`、`azure_speech_region` |
| 获取地址 | https://portal.azure.com → 语音服务 → 密钥和终结点 |
| 填写位置 | `config.toml` → `[tts]` 段 |
| 不填的后果 | 只能用系统 TTS，音色少、部分语言缺 |
```

## 安全提示（必须写进交付物）

1. Key **只落本地配置文件**，且确认该文件在 `.gitignore` 内

   ```bash
   git check-ignore -v config.toml   # 有输出才算安全
   ```

2. Key **不进文章、不进截图**（截图里出现 Key 要打码或重截）
3. 用**可吊销的测试 Key**，别用生产 Key
4. 分享 HTML 前全文搜一遍：

   ```bash
   grep -nEi "sk-[a-zA-Z0-9]{20,}|api[_-]?key\s*[:=]\s*['\"][^'\"]{8,}" article.html
   ```

   命中就说明漏了。

## 面向读者 vs 面向作者

问题单是**给读者看的**，不是你的待办清单。区别：

| 不要写 | 应该写 |
|---|---|
| "拿到 Key 后我会补齐 T1 部分" | 直接给字段、地址、位置、后果 |
| "请把你的 Key 发我" | 删除（这是写给协作方的话，不是读者） |
| "我测试用的是 xxx 的 Key" | 删除 |
| "未验证（无 Key）" | 「T2 项未验证：缺少 Azure 语音密钥，界面与配置项已确认存在」 |

最后一条是正确姿势：**说清未验证的是什么、为什么、已确认到什么程度**。这比含糊的"需要 Key"诚实得多。

---

## 验证后回头补

拿到 Key 之后：

1. 先跑最小请求验证 Key 有效（别直接上全流程）
2. 把「不填的后果」那一条从"预计"改成实测描述
3. 更新 T 档：跑通的降到 T0
4. 正文里把"未验证"替换成真实输出与截图

分档表在文章里保留完整，读者能自己判断要不要花钱。
