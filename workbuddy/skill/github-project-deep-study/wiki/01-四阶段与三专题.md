# 四阶段与三专题

## 为什么是这四段

四段不是拍脑袋分的，每段对应一个成熟的方法论，且各解决一类具体问题：

| 段 | 借用方法 | 解决的认知问题 |
|---|---|---|
| 熟悉 | 费曼 + 洋葱模型 | 我说不清它是干嘛的，说明我还没懂 |
| 学习 | C4 模型 + 第一性原理 | 我只能背 README 的架构图，说不出为什么这么设计 |
| 实战 | 可复现性 | 我没跑过，不知道文档和现实的差距 |
| 特性探索 | 产品经理视角 | 我说不出它到底能干什么、哪些功能是空壳 |

三段递进不是并列：熟悉是"外围层"，学习是"内核层"，实战是"验证层"。**跳过任何一层，写出来的东西都会停在转述层面。**

### 熟悉：练到能一句话讲清

合格判据是「电梯演讲」：30 秒内说清 **它是什么 + 把 X 变成 Y + 给谁用**。

不合格的例子：

> 这是一个基于 AI 的视频生成工具，功能强大，支持多种配置。

这句话可以套在任何视频工具上，等于没说。

合格的例子：

> 给一个主题，它自动写脚本、找素材、配音、加字幕、合成竖屏短视频，面向日更的短视频创作者。

差别在于：前者描述品类，后者描述**输入输出与替代掉的人工环节**。

### 学习：C4 四层 + 关键路径带行号

C4 是分层地图，四层必须都能填：

| 层 | 填什么 | 缺了会怎样 |
|---|---|---|
| Context | 系统边界、外部依赖服务 | 说不清它依赖谁，就说不清哪些功能会失效 |
| Container | 进程/服务构成（API、前端、worker、DB） | 说不清部署形态，就说不清怎么扩容 |
| Component | 模块职责与依赖方向 | 说不清模块，就找不到改动点 |
| Code | 关键类的关键方法（带文件名 + 行号） | 只能泛泛而谈，读者无法自查 |

关键路径必须落到 `文件:行号`，例如 `app/services/task.py:1516 _run_pipeline`。行号是**可验证锚点** —— 读者能立刻打开确认，你也没法糊弄自己。

ADR（Architecture Decision Record）问三个问题：**当时要解决什么、选了哪个方案、代价是什么**。只写"用了 FFmpeg"是描述，写"用 FFmpeg 而非 MoviePy，换来 4 倍合成速度，代价是要自己管进程与临时文件"才是决策。

### 实战：证明它真的会跑

实战段不是"安装说明"，是**证据段**。最低配置：

1. 克隆命令与真实输出
2. 依赖安装命令（含镜像等关键参数）+ 实际耗时
3. 启动命令 + 端口 + 探活结果
4. 至少两张真实截图（目录结构 + 界面首屏）
5. 踩坑表：现象 / 根因 / 处置

判据很硬：**读者照着你的命令能跑出同样结果**。所以命令必须是原文，不能是"配置好环境后执行启动命令"。

### 特性探索：从"能跑"到"能干什么"

能跑起来只是入场券。这一段回答：它有哪些能力、哪条路不花钱、哪些是宣传里的空壳。

八域枚举 + 特性矩阵 + 用户视角逐步操作 + 零 Key 验证，四件套见 [特性树与思维导图](05-特性树与思维导图.md)。

## 三专题怎么横切

三专题不是独立章节，是**贯穿全篇的三个视角**，最后在单独一节收口。

### 应用场景（5W1H）

| 维度 | 要回答的 |
|---|---|
| Who | 谁用：创作者 / 开发者 / 运营 / 内部工具 |
| What | 输入什么、输出什么、中间替代了哪些人工环节 |
| Why | 痛点是什么；不用它现在怎么做 |
| When-Where | 什么时机用；本地跑还是服务化 |
| How | 典型操作链路（几步、多久、要什么前置条件） |

写完再补两张表：**核心场景**（一定要用它）、**反例场景**（看着像能用，实际不该用）。反例表最能体现你真的想过。

### 边界思考（六维）

| 维 | 问法 |
|---|---|
| 适用 | 什么条件下它是最优解 |
| 不适用 | 什么条件下它是错的解（含官方声明的限制） |
| 性能 | 单次耗时、并发上限、瓶颈在哪一段（要实测数字） |
| 成本一致性 | 免费额度、按量计费、隐形成本（Key、GPU、带宽） |
| 运维 | 有状态吗、要不要持久化、升级会不会丢数据 |
| vs 同类 | 与两个最接近的替代方案比，各差在哪 |

「项目设计如此」的限制写这里，不写进踩坑表。例如路径白名单校验、枚举值严格匹配、单任务串行，都是设计取舍，不是 bug。

### 内核架构（一句话 + 链路图）

一句话公式：**「它是一个 <形态>，核心是 <机制>，靠 <扩展点> 获得灵活性」**。

> 它是一个串行阶段流水线，核心是把"脚本→素材→配音→字幕→合成"切成七个可单独失败重试的阶段，靠 Provider 注册表获得扩展性。

链路图画阶段与数据流，每段标函数名。不要画成"前端 → 后端 → 数据库"这种没有信息量的三层图。

## 时间预算

一次完整交付的经验分布（中型 Python 项目）：

| 阶段 | 占比 | 说明 |
|---|---|---|
| 枚举 + 读代码 | 20% | 决定后面写得深不深 |
| 环境与启动 | 25% | 变数最大，镜像与 SDK 是大坑 |
| 截图取证 | 15% | 流程实拍比想像中费时 |
| 零 Key 跑通 | 20% | 价值最高，也最容易卡在参数上 |
| 写 HTML | 15% | 有模板后很快 |
| 自检修补 | 5% | 别省，能抓出结构性错误 |

如果环境搭建超过 40%，说明踩到了环境坑，先看 [踩坑总表](09-踩坑总表.md) 再继续。

## 每段的失败信号

| 段 | 你已经走偏的信号 |
|---|---|
| 熟悉 | 电梯演讲里出现"强大""高效""一站式"这类形容词 |
| 学习 | 关键路径只有阶段名，没有函数名和行号 |
| 实战 | 截图是官方 README 里的图，或者自己画的流程图 |
| 特性探索 | 特性清单来自 README 的功能列表，没有实测标注 |
| 三专题 | 不适用场景一条都写不出来 |
