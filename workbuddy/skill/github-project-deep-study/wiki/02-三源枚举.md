# 三源枚举

特性清单**只从一个来源拿，一定会漏**。三个来源各能看到别人看不到的部分：

| 源 | 能看到 | 看不到 |
|---|---|---|
| 源码 | 注册表、扩展点、隐式能力、默认值 | 哪些真的接进了服务、参数怎么传 |
| 接口 | 真实端点、参数 schema、方法级口径 | UI 上的易用性封装、内部模块 |
| UI | 用户实际能点的功能、控件默认值 | 内部能力（没暴露到界面的） |

交叉之后问一句：**同一个能力，三源说的是否一致**。不一致的地方就是文章里最有价值的部分。

## 源 1：源码

```bash
python scripts/enum_features.py <repo> --depth 3
```

输出五节：

1. **目录结构** —— 先看形状，判断是哪类项目（单体/多服务/前后端分离）
2. **服务 / 模块层** —— `app/services`、`src/*`、`internal`、`pkg` 下的模块数
3. **注册表 / Provider 声明** —— 可插拔点，通常等于"能力清单"
4. **源码中的路由声明** —— 两种写法都要扫
5. **UI 层入口** —— 去这些文件里找控件文案

### 注册表用 ast 扫，不用正则

早期用正则 `\b([A-Z]\w*(?:Spec|Provider|Registry|Adapter))\s*\(\s*["']([a-z0-9_.\-]+)["']`，
结果把 docstring 里的示例 `XxxSpec("id", ...)` 也算进去，凭空多出 1 项。

现在走 `ast.walk`，只认真实调用表达式：

```python
for node in ast.walk(tree):
    if not isinstance(node, ast.Call) or not node.args: continue
    name = getattr(node.func, "id", None) or getattr(node.func, "attr", None)
    if not name or not name.endswith(("Spec", "Provider", "Registry", "Adapter")): continue
    if isinstance(node.args[0], ast.Constant) and isinstance(node.args[0].value, str):
        found.setdefault(name, []).append(node.args[0].value)
```

### 路由两种写法都要扫

```python
@router.get("/api/v1/ping")                       # 装饰器
router.add_api_route("/api/v1/task/{id}", f, methods=["GET", "HEAD"])   # 显式注册
```

只扫装饰器会漏掉后者，而且后者的 `methods` 列表必须展开 —— 一条路径挂两个方法时，**方法级端点数大于路径数**。这就是"计数口径"问题的来源，文章里要写明。

### 隐式能力从哪找

- `config.example.*` 的每个字段 = 一个可配置能力，注释里常带官方申请地址
- `requirements.txt` / `package.json` 里的重依赖 = 暗示了能力（`whisper` → ASR，`moviepy` → 合成）
- `docker-compose*.yml` 的变体数量 = 部署形态
- `i18n/*.json` 的数量 = 界面语言数
- `resources/` 下的静态资源数量 = 内置素材库规模

## 源 2：接口

服务起来后抓 `/openapi.json`：

```bash
python scripts/enum_features.py <repo> --api http://127.0.0.1:8080
```

或用 jq 直接算口径：

```bash
# 路径数
curl -s http://127.0.0.1:8080/openapi.json | jq '.paths | length'
# 方法级端点数
curl -s http://127.0.0.1:8080/openapi.json | jq '[.paths | to_entries[] | .value | keys[]] | length'
```

两条命令的数不一样是正常的：`download` / `stream` 这类端点常同时挂 `GET` 和 `HEAD`。**写文章时注明用的是哪个口径**。

接口是**权威源**：源码里有 18 个声明，openapi 里只暴露 13 条路径，说明有 5 个是内部路由或被条件注册掉了。这种差异本身值得写一句。

没有 openapi 的项目（桌面应用、纯 CLI）：源 2 换成 **项目自带的探测工具或 `--help` 输出**。例如 WPF 项目 `tools/PresetProbe` 的 stdout、CLI 的 `--help` 全量子命令列表。

## 源 3：UI

```bash
python scripts/shot_pages.py --api http://127.0.0.1:8080/docs --webui http://127.0.0.1:8501 -o shots/
```

UI 是**产品经理视角的功能清单**：把每个控件的标签抄下来，就是用户能碰到的全部能力。

- 下拉框的所有选项 = 一个枚举域
- 滑块的范围与默认值 = 可调参数的边界
- 输入框的 placeholder = 期望的输入格式
- 折叠区 / 高级设置 = 官方认为的"进阶能力"

Streamlit / Gradio 这类框架，控件文案直接来自源码字符串，UI 截图与源码能对上，天然是交叉验证。

## 交叉验证矩阵

枚举完填这张表，空格就是你的功课：

| 能力 | 源码有 | 接口暴露 | UI 可点 | 结论 |
|---|---|---|---|---|
| LLM Provider 切换 | ✔ 37 项注册表 | ✔ 通过参数 | ✔ 下拉框 | 三源一致，稳 |
| 字幕样式 | ✔ 6 项配置族 | ✘ 仅通过配置 | ✔ 部分 | 配置项多于 UI，UI 只是一部分 |
| 本地素材 | ✔ 白名单目录 | ✔ | ✔ 分组选择器 | UI 点击失效，需改配置 → 记入踩坑 |

空格处理原则：
- 源码有、接口无 → 内部能力，写"需改配置/内部使用"
- 接口有、UI 无 → API-only 能力，是差异化亮点
- UI 有、源码找不到 → 回头再找，可能在前端硬编码或远程配置

## 计数纪律

**数量类数字一律从模块导入或接口取，禁止 grep 手数。**

```bash
# 正确：从注册表拿
.venv/Scripts/python -c "from app.models import llm_provider as m; print(len(m.LLM_PROVIDER_REGISTRY))"

# 正确：从接口拿
curl -s /openapi.json | jq '[.paths | to_entries[] | .value | keys[]] | length'

# 错误：grep 然后肉眼数
grep -c "ProviderSpec(" app/models/*.py
```

实测教训：手数 Provider 得到 39，`len(REGISTRY)` 是 37（有两项被条件注册过滤）；手数端点 16，openapi 去重是 13 条路径 / 18 个方法级端点。

数字不值得自信，**导入一次就知道**。
