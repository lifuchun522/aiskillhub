严谨版

// 分布式互斥锁 + 双重检查，抑制缓存击穿
String getWithLock(String key) {
    String v = redis.get(key);
    if (v != null) return v;            // 第一重检查：已回填直接返回
    // 仅一个线程能拿到锁，其余自旋 / 短退避
    if (redis.setNX(lockKey, "1", 50ms)) { // 锁带超时，防死锁
        try {
            v = db.query(key);          // 单线程回源
            redis.set(key, v, ttl);      // 回填缓存（错开原 TTL，防集体过期）
        } finally {
            redis.del(lockKey);          // 释放锁
        }
        return v;
    }
    // 抢锁失败：短暂 sleep 后重试（或返回旧值 / 降级）
    Thread.sleep(20);
    return getWithLock(key);             // 第二重检查：回填后命中
}

白话版

把缓存想成餐厅的前台取餐口。平时客人（请求）直接在取餐口拿到套餐（命中缓存），厨房（数据库）很闲。某天套餐（热点 key）到点过期下架，一群客人同时涌到取餐口发现没饭了（缓存未命中）。如果不设规矩，所有人一窝蜂冲进厨房自己做饭（直接击穿 DB），厨房瞬间被挤爆。互斥锁就是在前厅放一个『单次只允许一人进厨房』的叫号器：第一个拿到号的人进厨房做一份饭并重新摆到取餐口，其余人在门口等几秒；等饭摆出来了，后面的人又回到取餐口直接拿，厨房恢复清闲。锁要带超时，否则做饭的人晕倒了（宕机），后面的人会永远在门口干等（死锁）。

自测题（含改变条件）

Q1
若去掉『双重检查』，只在外面判一次缓存空就抢锁，会有什么问题？
改变条件：改变条件：删除第一重 / 第二重缓存检查。
看答案
每个缓存未命中的请求都会去抢锁，即使缓存已被第一个线程回填。高并发下大量线程在锁外排队、重复回源，锁退化为全局串行，吞吐骤降，击穿没被真正抑制，只是换了个瓶颈。双重检查让回填后的请求直接命中，不再进锁。
Q2
若用『随机退避 + 不互斥』替代分布式互斥锁，能否抑制击穿？
改变条件：改变条件：去掉互斥锁，请求未命中时随机 sleep 后重试。
看答案
能缓解但不能根除。随机退避把回源请求在时间上打散，显著降低同一时刻打到 DB 的并发数，多数情况够用；但无法保证『恰好只有一个』线程回源，仍可能出现少量线程同时回源（退避窗口重叠），且重试会抬高尾延迟。互斥锁提供『单线程回源』的硬保证，随机退避是 softer 的工程折中。

适用场景

  • 热点 key 集中过期导致瞬时高并发回源（缓存击穿）
  • 秒杀 / 大促开场，少数 SKU 被海量请求争抢
  • 热点配置 / 元数据被突发流量击穿到数据库
  • 教学演示：把『锁如何串行化回源』讲清楚，而非做压测

限制

  • 本可视化是原理演示，不是 Redis 压测，不给出 QPS / 延迟实测数字
  • 示例用单实例语义；真实分布式锁需 Redlock / Redis 锁 + 看门狗，单节点锁在主从切换时会失效（锁丢失）
  • 锁必须带超时（防死锁），但超时过短会导致锁提前释放、出现双回源
  • 互斥锁把回源串行化，会抬高热点未命中期间的请求延迟（排队等待）
  • 它解决『击穿』（单 key 过期），不解决『雪崩』（大量 key 同时过期）与『穿透』（查不存在的 key）；三者机制不同
  • 锁竞争本身有开销；低并发场景用随机退避 / 逻辑过期更轻量

实践结论

缓存击穿的本质是『热点 key 失效瞬间，海量请求绕过缓存直击数据库』。互斥锁通过『单线程回源 + 双重检查』把并发回源压成一次，回填后其余请求回到缓存命中，从而抑制击穿。落地要点：锁带超时防死锁、回填缓存时错开 TTL 防集体过期、用看门狗兜底长回源；对延迟敏感且并发不极端的场景，随机退避 + 逻辑过期是更轻量的替代。该技能只演示机制，不替代真实压测与容量评估。
