# AI 原生应用技术架构设计文档

## 1. 文档目标

本文档定义一套**完整、可生成、可运行、可扩展**的技术架构，用于基于以下输入，生成并落地一个「本体模型驱动 + AI 大模型驱动」的 AI 原生应用系统：

- 原始业务需求（需求规格说明书）
- 本体模型 YAML 文件（M1 / M2 / M3 / M5 / M6 / M7 / MU 七模型）
- 本技术架构文档
- UI/UE 规范

本文档不描述某个单点功能，而是规定：

1. 采用什么**开发语言**与**开发框架**；
2. 如何组织**技术架构**与分层；
3. 如何实现**AI 融合的 Hybrid UI**；
4. 如何设计**自然语言对话**与能力编排；
5. 如何由本体模型**自动生成**前端、后端、数据库与 AI 工具能力。

后续 AI 大模型应严格依据本文档生成完整的前后端应用，并支持持续演进。

---

## 2. 架构定位

### 2.1 系统本质

本系统是一个：

1. 以本体模型作为业务语义核心的**模型驱动系统**；
2. 以 AI 大模型作为生成引擎和运行时智能交互引擎的 **AI 原生系统**；
3. 采用 **Hybrid UI**（固定界面 + AI 动态界面）模式的企业级轻量应用。

### 2.2 核心设计理念

本系统不是"先写程序，再补 AI"，而是：

1. 先沉淀业务语义模型；
2. 再基于模型自动生成程序骨架、页面、接口、数据库结构与 AI 工具能力；
3. 最终让 AI 在运行时继续基于同一套语义模型进行对话式交互和能力编排。

本体模型在系统中承担三重角色：

1. **业务建模载体**：表达对象、属性、行为、规则、流程、查询报表、界面等业务语义；
2. **程序生成基础**：供 AI 生成前端页面、后端 API、数据库结构和运行时注册表；
3. **AI 推理知识底座**：作为运行时 prompt/context 的结构化语义来源，提高 AI 对业务问题的理解精度与执行精度。

## 3. 技术选型总览

> 本节是全局技术约束，后续生成的所有代码必须严格遵循，不得擅自更换。

### 3.1 开发语言

| 层 | 开发语言 |
|---|---|
| 后端 | `Python` |
| 前端 | `TypeScript`（React JSX/TSX） |

### 3.2 开发框架与关键库

| 分类 | 选型 | 说明 |
|---|---|---|
| 后端 Web 框架 | `Flask` | 轻量、单体友好 |
| 后端数据访问 | `sqlite3`（标准库） | 不引入 ORM（SQLAlchemy 等） |
| 前端框架 | `React 18` | 组件化 |
| 前端样式 | `Vanilla CSS` | 遵循 CSS 变量与设计系统 |
| 前端图标 | `Lucide React` | 可选 FontAwesome CDN |
| 前端图表 | `ECharts`（echarts-for-react） | 统一图表主题 |
| 大模型 | OpenAI 兼容大模型（可配置） | 支持 Function Calling、SSE 流式；通过系统界面配置 Base URL / API Key / 模型 ID |
| 流式输出 | `SSE` | 服务端推送 |
| 构建工具 | `Vite` | 前端打包 |

### 3.3 核心约束

1. 后端 **单体分层**，不拆微服务；
2. 数据访问 **不使用 ORM**，统一使用 `sqlite3`；
3. 所有可变配置 **禁止硬编码**，走配置化；
4. 前端页面 **尽量元数据驱动**，不完全手写；
5. AI 对话与固定页面 **共用同一后端能力层**。

## 4. 总体架构

### 4.1 总体分层

整个系统采用单体应用、分层解耦的方式实现：

```
┌─────────────────────────────────────────────────────┐
│  前端 Hybrid UI 层（React + TypeScript）            │
│  ┌───────────────┐  ┌───────────────┐  ┌──────────┐ │
│  │ 固定功能界面   │  │ 多标签工作区   │  │ AI 对话区 │ │
│  └───────────────┘  └───────────────┘  └──────────┘ │
├─────────────────────────────────────────────────────┤
│  AI 编排层（意图识别 / 能力路由 / 工具调用 / 渲染）   │
├─────────────────────────────────────────────────────┤
│  后端服务层（Flask API / 行为 / 查询 / 规则 / SSE）  │
├─────────────────────────────────────────────────────┤
│  语义注册层（Ontology Registry）                     │
├─────────────────────────────────────────────────────┤
│  本体模型层（YAML 七模型，只表达语义）                │
├─────────────────────────────────────────────────────┤
│  数据存储层（SQLite）                                │
└─────────────────────────────────────────────────────┘
```

### 4.2 分层说明

#### 4.2.1 本体模型层

来源于用户提供的 YAML 本体模型文件（M1/M2/M3/M5/M6/M7/MU）。该层只表达语义，不直接承载运行逻辑。

#### 4.2.2 语义注册层

系统启动时首先解析全部本体模型 YAML，构建统一的运行时语义注册表 `Ontology Registry`。详见第 7 章。

#### 4.2.3 后端服务层

后端职责包括：

- 提供业务 UI 所需 REST API；
- 提供 AI 对话所需统一 API；
- 暴露行为/查询/规则等可复用能力接口；
- 执行本体模型驱动的校验、规则、查询与工具调用；
- 执行行为之间的同步联动（syncTriggers）；
- 向前端提供 SSE 流式响应。

#### 4.2.4 AI 编排层

负责把运行时对话请求，路由到：

1. 已有 API 能力；
2. 运行时工具函数；
3. 只读动态 SQL 查询；
4. 文本 / 表格 / 图表 / 操作建议 渲染协议。

本层接入 OpenAI 兼容大模型（可配置），支持函数调用。详见第 9 章。

#### 4.2.5 前端 Hybrid UI 层

前端由两类界面组成：

1. **固定功能界面**：对应本体模型 MU 中的界面建模；
2. **AI 动态界面**：在对话区域动态渲染文本、表格、图表、操作建议等内容。

详见第 5 章。

#### 4.2.6 数据存储层

数据库采用 `SQLite`，作为单体原型、本地轻量部署、MVP 数据底座。

## 5. Hybrid UI 架构（AI 融合界面设计）

### 5.1 设计目标

系统采用 `Hybrid UI` 模式，而不是纯固定菜单式 UI，也不是纯聊天机器人式 UI。

核心原则：

1. **高频、确定性、结构化**业务操作，提前提供固定 UI 页面；
2. **低频、探索式、分析式、临时性**需求，交给 AI 对话区动态完成；
3. 固定页面与 AI 动态渲染，**视觉风格必须统一**。

### 5.2 固定业务 UI

固定业务 UI 严格遵循本体模型 `MU` 模型文件，按其定义生成：

- **菜单树**：一级菜单 → 二级菜单（每个二级菜单对应一个界面）；
- **界面类型**：单表维护界面、主从表维护界面、查询列表界面、审批界面；
- **操作功能点**：每个按钮/动作对应一个 M2 行为。

界面布局遵循以下规范：

| 界面类型 | 布局规则 |
|---|---|
| 单表维护 | 一行 2 个属性控件；标签右对齐、控件左对齐；备注类长文本一行 1 个 |
| 主从表维护 | 主表一行 3 个属性控件；从表在下方表格化，数据维护/删除在表格内动态完成 |
| 模糊查询 | 查询条件区在上（一行 3 个属性控件）；结果表格在下，支持分页 |

控件类型映射（由 M1 属性类型决定）：

| 属性类型 | 界面控件 |
|---|---|
| 日期 / 日期时间 | 日期控件 |
| 枚举 / 数据字典 | 下拉列表框 |
| 对象引用（聚合根引用） | 跳选框（文本框 + 弹窗选择） |
| 布尔 | 复选框 |
| 长文本 / 备注 | 多行文本域 |
| 其它标量 | 文本框 / 数字框 |

带审批流程的功能界面，必须提供「保存草稿」与「提交」两个独立按钮功能点。

### 5.3 AI 动态 UI

AI 对话区支持以下渲染类型：

1. `text`
2. `table`
3. `chart`
4. `action`

说明如下：

- `text`：用于业务说明、状态反馈、执行结果说明；
- `table`：用于列表展示、统计结果、结构化查询结果；
- `chart`：用于趋势图、分布图、统计图，固定使用 `ECharts`；
- `action`：用于提示用户打开某个页面、查看详情、执行某个行为。

### 5.4 UI 一致性要求

固定页面与 AI 动态渲染必须统一以下风格元素：

- 统一色彩系统；
- 统一边框与背景体系；
- 统一表格风格；
- 统一图表主题；
- 统一文字（9pt 基准）与状态标签风格；
- 统一交互术语。

AI 对话框里渲染的表格与主工作台中的查询表格，应被视为同一设计系统下的不同承载容器。

### 5.5 工作台形态（三栏结构）

前端采用三栏结构：

1. **左侧**：导航树（菜单）；
2. **中间**：多标签工作区（固定功能界面）；
3. **右侧**：AI 智能助理（动态界面）。

交互约定：

- 左侧菜单与右侧 AI 对话区均支持显隐；右侧 AI 对话区宽度**支持拖拽调整**（中间工作区与 AI 对话区之间设置拖拽分割条，拖动实时改变宽度）。
- 右上角提供**用户菜单（下拉）**，至少包含：**修改密码**、**配置大模型**（仅管理员可见）、退出登录。

## 6. 本体模型驱动机制

### 6.1 驱动范围

本体模型不仅用于文档表达，还用于驱动以下能力：

1. 数据结构生成；
2. API 能力注册；
3. 页面表单生成；
4. 查询条件生成；
5. AI 工具定义生成；
6. 提示词上下文生成；
7. 数据库白名单生成；
8. 动态 SQL 查询边界生成。

### 6.2 模型到运行时的映射

#### M1 对象模型

驱动：

- SQLite 表结构；
- DTO 结构；
- 表单字段；
- 查询字段；
- 引用关系（外键）。

#### M2 行为模型

驱动：

- 业务执行 API；
- AI 工具函数；
- 前端按钮动作；
- 页面提交逻辑；
- **同步联动（syncTriggers）**：后端行为执行成功后同步调用下游行为，条件判断引用 M3 规则。

#### M3 规则模型

驱动：

- 后端参数校验；
- 前端提示规则；
- AI 工具调用前置验证；
- 同步联动中的条件判定。

#### M5 主体模型

对应到系统管理中的用户管理、角色管理、资源管理功能。当前已在技术底座中完整实现，MVP 阶段可采用简化策略（见第 12 章）。

#### M6 流程模型

对应到流程引擎中的流程设计、流程实例、任务管理等功能。当前已在技术底座中完整实现。

#### M7 查询报表模型

驱动：

- 跨对象查询 API；
- 报表导出；
- AI 查询工具；
- 结果列与聚合口径。

#### MU UI 模型

驱动：

- 导航树生成；
- 标签页生成；
- 表单和表格布局生成；
- 操作功能点与行为映射生成；
- AI 对话动作映射生成。

## 7. 运行时语义注册表 Ontology Registry

### 7.1 定位

`Ontology Registry` 是运行时的统一语义注册中心。

系统启动时加载全部 YAML，并生成内存结构，供以下模块统一使用：

- Flask API 层；
- AI 编排层；
- 前端元数据接口；
- 动态 SQL 白名单控制器。

### 7.2 注册表建议结构

建议注册表包含如下索引（与七模型一一对应）：

```python
registry = {
    "aggregates": {},                 # M1 聚合根
    "entities": {},                   # M1 子实体
    "data_dictionaries": {},          # M1 数据字典（驱动下拉选项）
    "aggregate_associations": {},     # M1 聚合关联（驱动外键与查询 Join）
    "behaviors": {},                  # M2 行为（含 syncTriggers）
    "rules": {},                      # M3 规则
    "actors": {},                     # M5 参与者
    "roles": {},                      # M5 角色
    "permissions": {},                # M5 权限
    "flows": {},                      # M6 流程
    "query_reports": {},              # M7 查询报表
    "screens": {},                    # MU 界面
    "menus": {},                      # MU 菜单（对应 application.menus）
    "api_capabilities": {},           # API 能力
    "ai_tools": {},                   # AI 工具能力
    "db_whitelist": {}                # 数据库白名单
}
```

### 7.3 注册表用途

#### API 能力注册

把 M2 中可执行行为、查询行为注册成统一 API 能力。

#### AI 工具注册

把可安全复用的行为、查询、规则、报表能力注册成函数调用工具。

#### 页面元数据注册

把 MU 模型注册成页面元数据，供前端动态生成页面骨架。

#### 数据库白名单注册

根据 M1 和查询行为，生成只读 SQL 可访问的表名、字段名、关联关系白名单。

## 8. 后端技术架构

### 8.1 技术选型

- Web 框架：`Flask`
- 数据访问：`sqlite3`（标准库，不用 ORM）
- 流式输出：`SSE`
- 配置管理：`YAML + 环境变量`
- 模型解析：YAML 解析器
- AI 调用：OpenAI 兼容大模型 API（可配置 Base URL / API Key / 模型 ID）

### 8.2 后端模块划分

建议后端至少划分为以下模块：

1. `app.py`（或 `main.py`）
2. `config/`
3. `ontology/`
4. `api/`
5. `services/`
6. `repositories/`
7. `ai/`
8. `sql_readonly/`
9. `sse/`
10. `utils/`

### 8.3 模块职责

#### `ontology/`

- 加载 YAML；
- 校验 YAML；
- 构建注册表；
- 输出运行时元数据。

#### `api/`

- 暴露 REST 接口；
- 参数接收与返回；
- 统一错误响应。

#### `services/`

- 行为执行；
- 查询执行；
- 规则执行；
- 同步联动（syncTriggers）执行。

#### `repositories/`

- 使用 `sqlite3` 访问数据库；
- 执行结构化查询；
- 执行增删改查。

#### `ai/`

- OpenAI 兼容大模型对接；
- prompt 构建（注入需求 + 本体模型 + API 能力 + 数据库表结构）；
- tool schema 注册；
- function calling 调用处理；
- 输出渲染协议转换。

#### `sql_readonly/`

- 动态 SQL 只读编排；
- SQL 白名单校验；
- 禁止 CUD/DDL；
- 查询结果限制。

#### `sse/`

- AI 流式输出；
- 事件分片推送；
- 最终结构化消息收口。

## 9. AI 编排与自然语言对话设计逻辑

> 本章是 AI 原生应用的核心，规定自然语言如何被理解、路由、执行与渲染。

### 9.1 AI 能力定位

AI 在本系统中承担四类职责：

1. **业务问答**；
2. **功能导航**；
3. **工具调用**；
4. **动态查询与可视化展示**。

### 9.2 模型供应商

运行时大模型采用 **OpenAI 兼容协议**接入，不绑定单一厂商（DeepSeek、通义、智谱、OpenAI 等均可）。配置项仅包含：

- Base URL（如 `https://api.deepseek.com`）；
- API Key；
- 模型 ID（如 `deepseek-chat`）。

其余参数一律采用默认值，其中 **`max_tokens` 默认值为 `81920`**（如目标模型对输出长度有上限，可在配置时调整）。

配置方式：通过系统界面（右上角用户菜单 → 配置大模型，仅管理员）进行，持久化到 `ai_config` 表；配置后提供**测试连接**能力（发起一次最小对话验证连通性，返回耗时、回复或错误信息）。禁止将 API Key 硬编码在代码或前端资源中。

### 9.3 对话消息模型

每次对话维护统一的消息结构：

```text
role: system | user | assistant
content: 文本内容
tool_calls: 工具调用请求（可选）
tool_results: 工具调用结果（可选）
```

- `system`：系统提示词，注入本体模型语义摘要、可用能力清单、安全边界；
- `user`：用户自然语言输入；
- `assistant`：模型回复或工具调用。

### 9.4 系统提示词（System Prompt）构成

系统提示词应基于本体模型动态构建，**必须注入以下四类业务语义，缺一不可**：

1. **软件需求概述**：业务域说明、核心业务对象与状态机（如合同/开票/收款的状态流转）；
2. **本体模型语义**：对象（字段）、行为、规则、流程、报表、数据字典（来自注册表）；
3. **系统只读 API 能力清单**：可调用的查询接口与工具清单；
4. **完整数据库表结构**：以**下划线命名的真实表名/字段名**列出每张表及其字段中文标签，并给出**关联关系说明**（如 `contract.department_id → department.id`、名称字段所在表），使模型能够正确生成 SQL（NL2SQL）。

此外还必须包含：

5. 系统角色与能力说明；
6. 只读安全边界（不得写数据）；
7. 渲染协议约定（何时返回 text/table/chart/action）。

### 9.5 意图识别与能力路由

AI 在接收用户问题后，按以下优先级做能力决策：

1. 是否已有**行为 API**（写操作）可用；
2. 是否已有**查询 API**（读操作）可用；
3. 是否已有**规则能力**可用；
4. 是否可使用**只读动态 SQL** 查询；
5. 若都不可用，则退化为**语义解释型回答**。

路由原则：

- 能调用 API 就不直接拼 SQL；
- 能调用标准查询就不走自由查询；
- 写数据必须走固定页面或明确的行为工具，AI 对话默认无 CUD 权限；
- **统计 / 聚合 / 按条件汇总 / 自定义列查询（如"按部门统计合同总金额""按合同类型统计""只要某两列"）：必须由 AI 自行构建 SQL（NL2SQL）通过 `readonly_sql_query` 工具动态查询，禁止使用返回固定列的查询/报表工具，以避免返回无关列；**
- 简单列表 / 详情可用固定查询工具，其余一律优先 NL2SQL。

### 9.6 工具定义（Function Calling）

系统必须支持 `Function Calling`。工具 schema 由本体模型自动生成：

#### 页面导航工具

- 打开某录入/维护页；
- 打开某查询页。

#### 查询工具

- 执行某列表查询；
- 获取某详情。

#### 行为工具

- 执行某录入/提交/审批行为。

#### 图表生成工具

- 将查询结果转换为柱状图 / 折线图 / 饼图。

#### SQL 只读工具（`readonly_sql_query`）

- 在缺少现成 API 能力，或需要统计 / 聚合 / 自定义列时，由 AI 自行构建只读 SQL 动态查询；
- 工具入参至少包含 `sql`（只读 SELECT）与 `chart_type`（`none` / `bar` / `line` / `pie`）；
- 当用户要求图表（"柱状图""折线图""饼图"）时，AI 必须设置 `chart_type`，结果按图表渲染；否则按表格渲染；
- 查询结果以「第一列为类别轴，其余数值列为序列」渲染图表；饼图以「第一列 + 第二列数值」渲染。

### 9.7 多轮对话与上下文管理

1. 后端为每个会话维护 `chat_session` 与 `chat_messages`；
2. 单次请求携带最近 N 轮对话作为上下文；
3. 上下文过长时进行**摘要压缩**（保留最近对话 + 历史摘要）；
4. 工具调用结果作为上下文回填，供模型继续推理。

### 9.8 结果渲染协议

工具执行结果按统一协议转换后返回前端：

| 渲染类型 | 触发场景 |
|---|---|
| `text` | 状态反馈、业务说明、执行结果 |
| `table` | 列表、统计、结构化查询结果 |
| `chart` | 趋势、分布、统计图（ECharts，支持 `bar` 柱状 / `line` 折线 / `pie` 饼图） |
| `action` | 引导用户打开页面、查看详情、执行行为 |

图表渲染约定：查询/只读 SQL 工具通过 `chart_type` 指定图表类型，前端用 ECharts 渲染；饼图数据为 `{name, value}` 结构，柱状/折线图为 `{name, 数值字段...}` 结构。

### 9.9 流式输出

AI 对话必须支持流式输出（SSE），消息分片如下：

1. `message_start`
2. `delta`
3. `tool_call`
4. `tool_result`
5. `render_payload`
6. `message_end`

前端据此实现：增量文本拼接、工具调用状态展示、最终结果切换为结构化渲染。

### 9.10 兜底与错误处理

1. 意图无法识别时，引导用户澄清或提供能力清单；
2. 工具执行失败时，返回明确错误说明并给出建议；
3. 用户请求写数据但无对应行为工具时，提示"请通过固定业务页面执行"；
4. 涉及敏感/越权操作时，明确拒绝并说明原因。

### 9.11 安全边界

1. AI 对话默认**只读**，禁止写数据；
2. 动态 SQL 严格只读，走白名单校验；
3. 所有工具调用记录审计日志；
4. 工具能力受权限边界约束。

## 10. 动态 SQL 只读方案

### 10.1 适用场景

当 AI 对话遇到以下情况时，可以启用动态 SQL：

1. 当前没有对应 API 能力；
2. 用户请求是数据读取类问题；
3. 问题可通过数据库直接查询回答。

### 10.2 严格边界

动态 SQL 必须严格只读，禁止以下语句：

- `INSERT` / `UPDATE` / `DELETE` / `REPLACE`
- `DROP` / `ALTER` / `TRUNCATE` / `CREATE` / `ATTACH`
- `PRAGMA` 写操作

如果 AI 判断用户请求需要写数据，必须明确回复：

> 当前 AI 对话能力仅支持只读查询，不具备新增、修改、删除权限。请通过系统固定业务页面执行对应操作。

### 10.3 安全控制

动态 SQL 模块至少要做以下限制：

1. 仅允许 `SELECT`；
2. 仅允许访问白名单表；
3. 仅允许访问白名单字段；
4. 强制追加 `LIMIT`；
5. 设置 SQL 执行超时；
6. 禁止多语句执行；
7. 记录审计日志；
8. 对 SQL 进行关键字与结构校验。

### 10.4 SQL 白名单来源

SQL 白名单不手工维护，而是从以下来源自动生成：

1. M1 对象模型；
2. 已登记的查询行为（M7）；
3. 预定义视图或统计口径。

白名单需与实际数据库表结构保持一致（表名、字段名均为**下划线命名**），并为每个字段建立**中文标签映射**（来自 M1 属性 label），同时注入系统提示词，供 AI 生成正确 SQL；字段的中文标签也用于查询结果的展示与图表序列命名。

### 10.5 动态 SQL 执行链路

1. 用户发起自然语言问题；
2. AI 判断：统计/聚合/自定义列查询，或当前无可复用 API 时，自行构建只读 SQL；
3. AI 请求 `readonly_sql_query` 工具（携带 `sql` 与可选 `chart_type`）；
4. 后端根据注册表校验目标表和字段是否合法；
5. 执行只读 SQL；
6. 把结果转成 `text/table/chart`（按 `chart_type` 渲染柱状/折线/饼图或表格）；
7. 通过 SSE 返回前端。

## 11. 数据库架构

### 11.1 数据库选型

数据库固定使用 `SQLite`。适用原因：部署简单、原型开发快、单体应用足够轻量、便于 AI 快速落地。

### 11.2 建表来源

数据库结构主要由 M1 对象模型映射生成。映射策略：

| 对象类型 | 映射策略 |
|---|---|
| 聚合根 | 一张主表（MASTER） |
| 子实体（集合） | 从表（DETAIL），外键关联主表 |
| 子实体（单个） | 主表字段平铺 |
| 值对象 | 字段前缀平铺或 JSON 列 |
| 聚合间关联 | 外键字段（FK，存储目标聚合根 ID） |
| 数据字典引用 | 存储字典 `code` 的列 |

### 11.3 建议表

业务表由 M1 模型自动生成（表名、字段名随模型变化），系统表固定包含：

1. `users`（登录用户）
2. `chat_sessions`（对话会话）
3. `chat_messages`（对话消息）
4. `audit_logs`（审计日志）
5. `ai_config`（AI 大模型配置，单行：base_url / api_key / model_id / max_tokens，默认 max_tokens=81920）

### 11.4 登录用户表

当前不实现完整 RBAC，但需要登录，因此保留轻量登录表：

- 用户名；
- 密码哈希；
- 是否启用；
- 显示名称。

默认提供一个具备全部功能权限的管理员账号。

## 12. 登录与权限策略

### 12.1 当前阶段策略

1. 系统必须支持登录；
2. 默认提供一个拥有全部功能权限的账号；

### 12.2 与本体模型的关系

M5 主体模型保留，当前主要作为：

- 语义占位；
- 后续扩展基础；
- 页面和能力边界说明。

MVP 阶段后端采用简化策略：登录成功后统一授予全部功能访问权，不做细粒度角色隔离。

### 12.3 后续扩展能力

后续启用 RBAC 时，可直接基于 M5 扩展：菜单权限、页面权限、API 权限、AI 工具权限、数据范围权限。

## 17. 生成导向要求

该架构文档服务于后续 AI 自动生成程序，生成时必须遵循：

1. 优先生成可运行单体，而不是过度拆分微服务；
2. 优先保证本体模型与代码的一一映射关系；
3. 优先复用统一 API 与统一语义注册表；
4. 固定页面与 AI 对话能力必须共用同一后端能力层；
5. 所有 AI 动态查询必须经过只读安全控制；
6. 对于暂未建模的业务能力，AI 可解释，但不得擅自执行写操作；
7. 前端严格遵循 Hybrid UI 与设计系统（9pt 基准、标签右对齐控件左对齐、单表 2 列 / 主从表 3 列 / 查询 3 列）。

## 18. 关键结论

本系统的核心不是某个技术框架，而是「**本体模型 + 运行时语义注册表 + 可复用 API + AI 工具调用**」的统一闭环。

最终落地形态应满足：

1. 本体模型能生成固定业务 UI；
2. 本体模型能生成后端 API；
3. 本体模型能为 AI 提供运行时知识语义；
4. AI 对话能优先复用现有业务能力；
5. 当没有 API 能力时，AI 只能通过严格只读 SQL 查询补位；
6. 固定页面和 AI 动态界面共享同一设计系统和同一业务能力层。

这套架构不绑定任何具体业务域，可作为通用 AI 原生应用底座，支撑多业务域的持续扩展。
